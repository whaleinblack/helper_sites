# Helper Sites 通用技术与视觉规范

> 版本：1.0  
> 更新日期：2026-08-26  
> 适用范围：本仓库未来新增、迁入和维护的所有 `helper site`

## 1. 文档目的

本规范定义 `helper_sites` 仓库内所有独立网站的共同底线，包括目录、工程、数据、安全、可访问性、离线交付、Git 工作流与默认视觉语言。

它不是某个具体网站的产品规范。每个站点仍应根据任务建立自己的信息架构、品牌和交互，但不得降低本文规定的工程质量与可用性。

本文使用以下强度词：

- **必须**：合并前必须满足；确实不适用时，要在站点 README 说明原因。
- **应该**：默认遵循；偏离时需要有明确产品理由。
- **可以**：按站点需要选用。

## 2. 总体原则

1. **一个站点，一个独立边界**：每个站点可独立安装、运行、测试、构建和发布。
2. **先解决任务，再增加装饰**：首屏必须让用户立即知道网站做什么、主要结论或主要操作在哪里。
3. **真实数据可追溯**：涉及价格、政策、统计、项目状态等时，必须标注来源与数据日期。
4. **默认安全**：密钥、账号信息、私有部署 ID 和个人数据不得进入 Git。
5. **默认可访问**：键盘、触控、不同屏幕尺寸和减少动画偏好都应能正常使用。
6. **避免过早共享**：同一种实现至少稳定复用三次，再考虑抽成仓库级模板或共享包。

## 3. 仓库与目录结构

```text
helper_sites/
├─ docs/
│  └─ helper-site-standards.md
├─ sites/
│  └─ <site-id>/
│     ├─ README.md
│     ├─ package.json
│     ├─ package-lock.json
│     ├─ .env.example          # 仅在需要环境变量时
│     ├─ app/ 或 src/
│     ├─ public/
│     ├─ tests/
│     └─ offline/              # 仅在提供离线单文件时
├─ templates/
├─ sites.json
└─ README.md
```

### 3.1 站点目录规则

- `site-id` 必须使用小写英文、数字和连字符，例如 `invoice-helper`。
- 站点源码、依赖、配置、测试和说明必须留在自己的目录内。
- 站点之间不得通过 `../../other-site/src` 直接引用源码。
- `node_modules/`、构建缓存、测试输出和本地日志不得提交。
- 构建产物默认不提交；用户明确需要下载的离线 HTML、PDF 等交付物除外。

### 3.2 `sites.json` 登记规则

每次新增、迁移、归档或重命名站点，必须同步更新根目录 `sites.json`。每项至少包含：

```json
{
  "id": "site-id",
  "title": "面向用户的标题",
  "description": "一句话说明",
  "path": "sites/site-id",
  "stack": ["React", "TypeScript"],
  "status": "active"
}
```

`status` 使用 `active`、`maintenance` 或 `archived`，不自行创造同义状态。

## 4. 每个站点必须具备的说明

站点 README 至少记录：

- 用途、目标用户和核心任务；
- 数据来源、数据时间与已知限制；
- 所需 Node.js / 包管理器版本；
- 安装、开发、测试和生产构建命令；
- 所需环境变量及其“公开配置 / 服务端秘密”属性；
- 发布方式，以及是否提供离线版本；
- 与常规规范不同的决定及原因。

代码中的产品概念应采用稳定名称。一个概念第一次出现在文档时，建议给出规范英文名和中文名；后续不要随意切换近义词。新增复杂面板或模块时，应记录名称、层级、默认状态、入口、主要职责和边界。

## 5. 工程标准

### 5.1 技术栈

- 交互型站点默认使用 **React + TypeScript**。
- 构建器可以使用 Vite、Vinext 或项目已有且仍受维护的方案；不得只为统一而替换正常工作的架构。
- 必须提交锁文件，并使用与锁文件一致的包管理器。
- 运行时版本必须在 `package.json#engines` 或 README 中声明。
- 能用浏览器标准能力完成的功能，不新增重量级依赖。

### 5.2 脚本命名

适用时优先提供下列一致入口：

```json
{
  "scripts": {
    "dev": "启动本地开发",
    "build": "生产构建",
    "test": "自动化测试",
    "lint": "静态检查",
    "build:offline": "生成离线单文件"
  }
}
```

合并前必须成功执行生产构建。存在测试或静态检查脚本时，也必须运行相关检查。

### 5.3 代码边界

- 页面负责组合，业务数据、格式化和计算应放到明确的数据或工具模块中。
- 第三方服务差异应收敛在 adapter / service 层，不散落到展示组件。
- 重复出现且语义相同的交互应复用组件；仅外观相似、职责不同的组件不要强行合并。
- 不保留无用的示例、脚手架占位内容、调试接口和未使用依赖。
- 错误状态必须可见且可恢复；不得让失败只表现为空白页面。

## 6. 数据、来源与内容标准

- 时效性数据必须标出“数据截至”或“最后核验”日期。
- 页面应尽可能链接到原始、官方或第一方来源。
- 推算值、预算带和评分必须与官方统计或真实成交值明确区分。
- 数据样本不足时，应显示限制说明，不用伪精确小数掩盖不确定性。
- 外部链接使用清晰名称；新窗口打开时添加安全的 `rel` 属性。
- 中文内容统一使用 UTF-8，避免乱码和不可见控制字符。

## 7. 安全与隐私

- `.env`、API key、token、密码、Cookie、个人地址和私有项目 ID 不得提交。
- 仅可公开的浏览器配置才允许进入前端 bundle，并应在服务商侧限制域名和权限。
- 服务端秘密必须通过环境变量或托管平台 secret 注入。
- 生产环境默认关闭调试、内部检查接口和浏览器直连秘密 API 的 fallback。
- 站点若收集分析数据，README 必须说明工具、事件、数据范围和关闭方式。
- 未明确需要时，不采集身份信息、精确位置或跨站追踪信息。

## 8. 通用视觉系统

本节是新站点的默认视觉基线，提炼自参考项目的 UI 文档和样式系统。它提供一致的家族感，但不是要求所有站点采用同一种页面布局。

### 8.1 视觉方向

- 整体气质：清晰、安静、可信赖，信息密度高但不拥挤。
- 重要内容依赖排版、留白、色彩层级和真实内容建立视觉焦点。
- 浮动工具、面板和状态卡可以使用轻量玻璃质感；长文、表格和密集数据区优先使用稳定的不透明底色。
- 禁止无目的堆叠渐变、发光、阴影、玻璃层和大面积动画。
- 每个站点应有一个明确的主色和一个语义强调色；警告色不能代替普通装饰色。

### 8.2 默认字体

```css
font-family:
  "Segoe UI",
  "PingFang SC",
  "Microsoft YaHei",
  "Noto Sans SC",
  system-ui,
  sans-serif;
```

- 正文默认 `16px`，最小辅助文字原则上不小于 `12px`。
- 正文行高建议 `1.55–1.75`，长文单行建议控制在 `60–80` 个拉丁字符的视觉宽度。
- 标题可使用 `clamp()` 建立响应式层级；避免靠极粗字重和全大写表达所有层级。
- 数字、价格和时间应使用支持等宽数字的字体特性，便于比较。

### 8.3 默认颜色与 token

新站点应该在自己的全局样式中定义语义 token，而不是在组件里反复写颜色值。推荐基线：

```css
:root {
  --hs-text: #14213d;
  --hs-text-muted: rgba(20, 33, 61, 0.72);
  --hs-page: #f4f7fb;
  --hs-page-alt: #e8eef6;
  --hs-surface: rgba(255, 255, 255, 0.72);
  --hs-surface-strong: rgba(255, 255, 255, 0.86);
  --hs-border: rgba(255, 255, 255, 0.68);
  --hs-shadow: 0 22px 60px rgba(18, 40, 68, 0.16);
  --hs-panel-shadow:
    inset 0 1px 0 rgba(255, 255, 255, 0.72),
    0 18px 48px rgba(15, 76, 129, 0.16);
  --hs-accent: #2d79bf;
  --hs-accent-strong: #145487;
  --hs-warm: #d96b41;
  --hs-danger: #c53f3f;
  color-scheme: light;
}

:root[data-theme="dark"] {
  --hs-text: #e5edf7;
  --hs-text-muted: rgba(229, 237, 247, 0.72);
  --hs-page: #08111f;
  --hs-page-alt: #0c1522;
  --hs-surface: rgba(10, 18, 30, 0.64);
  --hs-surface-strong: rgba(12, 21, 34, 0.78);
  --hs-border: rgba(148, 163, 184, 0.18);
  --hs-shadow: 0 22px 60px rgba(2, 6, 23, 0.45);
  --hs-panel-shadow:
    inset 0 1px 0 rgba(255, 255, 255, 0.04),
    0 18px 48px rgba(2, 6, 23, 0.36);
  --hs-accent: #68a5e0;
  --hs-accent-strong: #d8ebff;
  --hs-warm: #f39c73;
  --hs-danger: #ff9b97;
  color-scheme: dark;
}
```

站点可以替换品牌色，但必须保留语义命名、文本对比度和浅/深色的完整对应关系。

### 8.4 间距、圆角与布局

- 基础间距序列：`4 / 8 / 12 / 16 / 24 / 32 / 48 / 64px`。
- 页面桌面端外边距默认 `16–24px`，移动端默认 `12–16px`。
- 卡片间距默认 `12–16px`；卡片内边距默认 `14–24px`。
- 常规圆角使用 `12 / 18 / 24px`；胶囊和圆形控件使用 `999px`。
- 桌面端内容区必须设置合理 `max-width`，不要让长文本或表格无限拉宽。
- 使用 CSS Grid / Flex 和 `clamp()`；不要用只适合单一屏幕的绝对坐标搭主要页面。
- 参考响应断点：`1450px`、`1320px`、`960px`、`720px`。具体站点应由内容实际断裂位置决定最终断点。

### 8.5 表面、控件与状态

默认玻璃面板可以使用：

```css
.hs-glass-panel {
  border: 1px solid var(--hs-border);
  background: var(--hs-surface-strong);
  box-shadow: var(--hs-panel-shadow);
  backdrop-filter: blur(20px) saturate(1.18);
}
```

- 玻璃面板必须有不支持 `backdrop-filter` 时仍可读的背景色。
- 主操作按钮应明显但数量有限；次要操作使用边框、文字或低对比表面。
- Hover 和键盘 Focus 应共享视觉反馈，Focus 不得被简单移除。
- 危险操作必须有独立的危险色和清晰文案，不仅依赖图标。
- Loading、Empty、Error、Disabled、Success 状态都应有明确设计。
- 图标必须有可理解的文本、提示或 `aria-label`，不能只靠图形猜测含义。

### 8.6 动效

- 普通 hover、focus、面板和浮动控件过渡默认 `160–180ms`。
- 优先使用轻微位移、阴影或内容高亮；常规 hover 位移不超过 `1–2px`。
- 已使用 `transform` 定位的元素，交互态必须保留原定位变换。
- 复杂拖拽或展开可以更长，但应以状态清晰为目标，避免拖尾和装饰性等待。
- 必须支持 `prefers-reduced-motion: reduce`，关闭非必要移动和自动动画。
- 动画不得阻塞输入、数据读取或主要内容出现。

### 8.7 浅色与深色主题

- 若站点提供深色模式，则浅色与深色必须功能、信息和焦点状态对等，不能视为两套布局。
- 主题切换应通过根节点属性和语义 token 完成，避免在组件中散布大量硬编码覆盖。
- 图片、地图、图表、logo 和第三方组件都必须检查两种主题下的可读性。
- 未提供主题切换的站点，也必须正确声明 `color-scheme` 并避免浏览器控件颜色冲突。

## 9. 响应式与可访问性

- 必须至少覆盖桌面、平板和手机宽度，不得出现横向页面溢出。
- 触控目标建议不小于 `44 × 44px`；密集桌面工具不得小于 `40 × 40px`。
- 所有关键操作必须可通过键盘完成，并有可见的 `:focus-visible` 状态。
- 使用语义 HTML：标题顺序合理，按钮使用 `<button>`，导航使用 `<nav>`，数据表使用 `<table>`。
- 表单控件必须有关联 label；错误信息应说明原因与修复方法。
- 文本和关键 UI 应满足 WCAG 2.2 AA 对比度；不能只用颜色表达状态。
- 图片必须有适当的 `alt`；纯装饰图使用空 `alt` 或隐藏于辅助技术。
- 弹窗、抽屉、菜单需管理焦点、Escape 关闭和背景交互。
- 表格和图表在窄屏应可滚动、改为卡片或提供文本摘要，不能简单缩小到不可读。

## 10. 性能与可靠性

- 首屏不得依赖不必要的第三方脚本才显示核心内容。
- 图片应使用合适尺寸和格式，并设置宽高以避免布局跳动。
- 对大列表、地图、图表或搜索使用延迟加载、缓存或节流。
- 默认性能目标：LCP ≤ 2.5s、CLS ≤ 0.1、INP ≤ 200ms（在合理的中端设备和网络条件下）。
- 非地图型 helper site 的首屏 JavaScript gzip 目标应控制在 `200KB` 左右；超出时在 README 说明主要原因。
- 网络失败、权限不足和空数据必须有可理解的 fallback，不得白屏。
- 运行时错误应至少在页面上提供简短错误信息和重试/刷新建议。

## 11. 离线单文件交付

用户要求“下载后直接打开”时，输出统一放在：

```text
sites/<site-id>/offline/<site-id>.html
```

离线文件必须满足：

- HTML、CSS、JavaScript、字体和必要图片全部内嵌，或使用无需联网的 `data:` URL；
- 不含相对静态资源路径、外部 stylesheet 或外部 script；
- 不使用浏览器会按本地文件限制的 ES module 启动方式，优先输出普通 IIFE 脚本；
- bundle 不得残留 `process.env`、CommonJS `require()` 等服务器运行时依赖；
- 所有核心数据和交互离线可用，只有主动点击外部来源链接时才允许联网；
- 必须用 `file://` / 双击文件的实际打开方式验证，不能只在 localhost 验证；
- 构建脚本应检查外部依赖、服务器变量和缺失 root 元素，失败时直接终止；
- 页面启动异常时必须显示 fallback 错误信息，不能保持空白。

## 12. 测试与验收

每次交付至少检查：

### 功能

- 主要任务完整可走通；
- 筛选、切换、排序、链接和表单按预期工作；
- 加载、空数据、错误和重试状态存在；
- 刷新和直接打开深链接不会丢失必要状态。

### 视觉与交互

- 桌面、平板、手机无内容遮挡或横向溢出；
- 标题、正文、辅助信息和操作层级清楚；
- Hover、Focus、Active、Disabled 和危险状态可区分；
- 浅/深色主题（若有）均可读；
- 动画在减少动画模式下正确降级。

### 工程

- 生产构建成功；
- 自动化测试和静态检查成功，或 README 记录暂缺原因；
- 无密钥、私有 ID、调试输出和无用依赖；
- README、`sites.json`、数据日期和来源已更新；
- Git diff 仅包含本次任务相关内容。

## 13. Git 工作流

- `main` 保持可构建、可交付，不直接提交未经验证的大改动。
- 新站点和显著改动使用描述性分支，例如 `codex/<site-id>` 或 `feature/<site-id>-<topic>`。
- 一个 PR 只解决一个站点或一个清晰主题，避免混入无关格式化。
- 提交信息使用祈使语气并说明结果，例如 `Add offline build for invoice helper`。
- 合并前确认分支已同步、工作区干净、构建通过，且 PR 说明包含验证结果和已知限制。
- 不使用会覆盖他人修改的强制重置或强推，除非仓库所有者明确要求。

## 14. 模板与共享资产

- `templates/` 只保存已经反复验证的脚手架、token 或组件约定。
- 共享模板必须提供版本、使用说明、包含范围和升级方式。
- 模板更新不得自动破坏既有站点；迁移由各站点单独验证。
- 不复制参考项目的业务专用组件、logo、文案或地图逻辑作为全局模板。

## 15. 参考基线与取舍

本规范的视觉部分参考了 `chufa.wang-main` 项目中的：

- `docs/ui-guideline.md`
- `docs/ui-terminology.md`
- `src/styles/global.css`
- `src/styles/reset.css`
- `src/styles/shell.css`
- `src/styles/status.css`

保留为通用基线的内容包括：语义 token、浅/深色对等、蓝色主色与暖色状态、克制的玻璃表面、统一间距和圆角、短而柔和的动效、响应式缩放、可复用组件和稳定术语。

没有纳入通用规范的内容包括：旅行规划器专属的地图布局、Planning Panel、Day tabs、路线编辑阶段、地图镜头参数、天气与交通规则。这些属于参考项目的业务规范，不应约束其他 helper sites。
